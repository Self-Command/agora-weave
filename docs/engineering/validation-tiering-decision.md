# 分层开发验证与正式验收决定

日期：2026-10-15。宪法由 3.0.1 升至 3.1.0：在第四条实质扩充开发验证、开发准入和正式验收之间的规则；
未删除质量门槛、改变产品需求或云端执行地点，按治理规则升次版本。首次批准日期仍为既有 TODO，不能以本次批准代填。

## 批准依据与适用范围

用户明确批准：“开agent然后按照你建议修改工作流程和宪法。第一阶段现在允许你使用你当前的建议来执行。当前阶段完成后提交pr和保持工作区干净。然后给我交接提示词我开新窗口执行sk-sp-br”。

该批准按原宪法第九条解决原先“完整 T027 ci-ready 是任何业务开发前置”的实质冲突，适用于当前初始化阶段及后续开发流程。
批准采纳的方案是：逐行为云端 Red→Green 与受影响测试／必要回归；基础构建、测试通道及所需服务健康后可开发；
不影响目标行为验证的 CI 证据问题并行修复；合并、阶段验收交付及发行前仍完成同 SHA 全部适用验证；失败、跳过及缺失永不算通过。
ED-11–18、285 个 canonical 任务及未完成状态、原需求追溯和产品／平台验收范围保持有效。

## 三种结论与证据

| 结论 | 真实证据与允许动作 | 不能推导 |
| --- | --- | --- |
| development-ready | Actions 实际固定依赖安装／构建、非空目标测试通道、所需隔离服务健康及原报告可认证；源 run／attempt、SHA、事件／checkout、清单和稳定基础输入摘要绑定；可沿原 DAG 做业务 TDD | T027、完整矩阵、任务或阶段验收已通过 |
| ci-ready | T026／T027 同一最终初始化 SHA 的完整必需集合：最低／当前 iOS 和 Android、Web、官方服务、增量编排、拒绝探针、归档清理及当前 Codex 代码／实际图像审查，报告实际读取 | 业务 AC、产品首次图像基准、feature complete 或生产批准 |
| 正式合并／阶段验收／发行 | 当前最终 SHA 及匹配产物的全部适用验证、权限安全、真实交互、最低／当前系统及代码／实际图像审查，处置完缺陷及必要具体基准确认；发行另需全首版集合与具体生产批准 | Draft PR 或工程移交可替代验收 |

development-ready 使用独立认证记录，不复用 ci-ready 标志或缩减后的正式清单。记录基础源提交与目标提交的祖先关系，
核工作流、测试执行器／门禁、治理契约、固定依赖／工具链及环境的稳定 foundation 摘要；普通业务变更仅在基础输入未漂移时沿用该基础准入。
基础输入发生变化须重新核验相应基础证据；未知输入、无原报告、错 SHA／attempt 或不健康前置不能认证为 development-ready。
业务新增的接口／迁移／夹具／端组件仍须在其行为 Red 前接入非空真实执行；不能借基础准入跳过当前目标的安全或实际依赖。

每个新行为仍须云端语义 Red、实际读取因果、实现、同 oracle／fixture Green。
正式开发 Green 运行受影响套件及必要回归，由真实 diff、依赖、任务／契约和风险冻结集合；未知或无法确认的影响采用完整适用集合。
工程门禁、清单、调度、缓存及取证行为也是目标行为，须有对应 Red→Green，不按普通文档免测。
快速反馈只提供诊断，不能升级为 Green；当前范围的 Green 不能升级为完整 ci-ready、任务验收或发行通过。
无关完整矩阵或证据完备性缺口可并行处置；基础不健康、目标结果不可认证、安全未知只阻塞依赖工作。

保留全部 285 个任务 ID、任务验收责任和勾选状态，不重新生成任务、不补造历史 Red、Green、ci-ready 或完成记录。
