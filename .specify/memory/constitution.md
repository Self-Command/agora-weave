# 项目宪法

本宪法仅规定稳定的产品、技术、质量、安全与授权边界。具体开发流程、测试策略、
证据格式、收据、工具和状态规则由工程说明承载，不作为宪法硬门槛。

## 核心原则

### 一、产品结果与代码质量

以已批准的可用功能为交付结果。代码职责清晰、边界明确，优先复用成熟能力。
抽象、依赖和工程设施须有当前需求与维护依据，避免为流程完整而增加无关复杂度。

### 二、产品与架构边界

保持已批准产品范围及模块契约。核心身份、权限、安全、配置和必要审计不能因业务扩展停用而失效。
扩展隔离权限、数据和环境；版本、依赖、兼容与恢复限制必须真实可识别，不承诺未经验证的无损恢复。

### 三、安全、隐私与 AI 边界

实行最小权限和最小必要数据，由服务端核验当前身份、资源与操作资格。
历史授权、JWT、缓存、工具或高权限凭据不能绕过当前限制；撤权后后续新访问须按当前资格拒绝。
秘密与无关私人数据不得暴露给客户端、日志或公开产物。产品 AI 及其 MCP 保持只读并只处理获准数据。

### 四、真实测试与可靠结果

按实际变更与风险进行有效测试。关键权限、安全、数据完整性以及修复的缺陷必须有对应有效测试。
功能结论来自真实运行；编译成功、静态检查或 mock 演示不能单独证明业务完成。
失败、未执行、跳过、取消、超时及环境故障不得伪装为通过；修复后复测受影响行为。
保留真实结果和必要日志，不删除有价值的测试，不因历史证明不完整而重做正常代码。

### 五、环境与生产隔离

开发、测试与生产的数据、凭据和副作用必须隔离；开发测试不得使用未经授权的生产秘密或真实用户资料。
生产常驻服务独立部署。开发验证或云端通过不自动授予生产操作、发布或用户专属基准确认。

### 六、真实体验与原生可用性

所有前端页面，包括移动 App、Web、管理后台及插件界面，必须以已批准的
`docs/design/UI-SPEC.md`、`docs/design/design-tokens.json` 和 `docs/design/prototype/`
内的 HTML／CSS／JS 原型为设计依据。实现前须实际查看适用原型的画面与交互，理解其风格和原生体验；
原型未绘制具体页面时，沿用既有组件、视觉层级和交互规则，按对应端补齐业务状态，不另起一套视觉。
不得以先跑通功能、通用表单或原生默认样式为由跳过设计落实。

新增或修改前端页面时，必须先将对应页面和适用状态补入现有 HTML 原型入口，提交用户验收；
只有用户明确验收通过后，才可依据该版原型开发或调整生产页面。未通过时继续修改原型，
不得先实现生产页面再补原型，也不得把沉默、原型可运行或代理自评视为用户验收。
原型须与现有原型导航、主题和组件风格统一维护，不另建互不关联的设计稿。

各端遵守已批准设计及一致组件语义，适配字体缩放、对比度、触控、读屏、焦点与安全区。
加载、失败、权限变化与不可用状态提供真实反馈。原生交互和视觉结论须来自对应客户端实际运行。
页面完成须包含相应批次中与设计规范及原型对照后的实际界面与交互复检；功能可用或测试通过
不能单独证明设计符合。原型中的虚构数据、演示权限与历史业务状态不能覆盖当前产品和安全规则。

### 七、性能与资源纪律

性能结论来自可复现测量并说明环境、数据规模、负载及口径，不作无依据的性能承诺。
资源和额外基础设施须说明当前用途及成本，不产生未经用户批准的费用。

### 八、生产内容与可维护性

生产代码、注释、界面与运行输出仅保留产品功能、运行、安全和维护所需内容。
开发对话、任务进度和 AI 自评放在独立工程资料中；清理不得误删真实功能、有效测试或必要证据。

### 九、用户决策与授权

在已批准目标、技术栈和安全边界内自主处理普通、可逆的工程选择，不反复确认既定决定。
改变已确认产品范围、技术栈、安全或隐私边界，产生费用，执行不可逆删除／高影响数据迁移或生产操作，
须先向用户说明具体对象、影响及可选方案并取得明确决定；需要确认时使用可用的原生卡片。
只暂停依赖该决定的工作。沉默、超时、预选选项及代理判断不能代替用户批准。

## 长期技术约束

- 移动端使用 Expo、React Native 和 Expo UI，覆盖 iOS 与 Android。
- 后端使用 Supabase 官方 Docker Compose 自托管。
- 管理后台基于 Kiranism 的 Next.js、shadcn/ui 模板。
- 产品完整范围和正式功能验收要求由 PRD、规格及设计承载，不因开发流程精简而自动删除。

## 文档职责

需求与业务规则由 PRD／spec 承载，技术方案由 plan 承载，实施与局部进展由 tasks 承载。
工作流及工具配置遵守已批准的工程说明；SP／SK 默认流程服从项目明确规则，不反向恢复已取消的过程门禁。

## 治理

稳定原则的实质修订须取得用户批准并记录依据；普通工程选择按第九条自主处理。
版本采用语义化规则：不兼容原则重定义升主版本，新增原则升次版本，文字修正升修订版本。
本次 4.0.0 → 5.0.0 依据 2026-10-16 用户明确批准的业务优先精简方案、四项补充及三项执行优化。
批准与同步记录见 `docs/engineering/business-first-development-decision.md`。
本次 5.0.0 → 5.1.0 依据 2026-10-16 用户明确要求：所有前端页面必须参考 UI 设计规范和 HTML 原型，
并先理解原型风格与原生体验；扩充第六条设计依据与真实复检要求，其他稳定原则和技术栈不变。
本次 5.1.0 → 5.2.0 依据 2026-10-16 用户明确决定：每次页面开发先制作与现有入口关联的原型，
经用户明确验收后再实现生产页面；不采用先开发移动网站再转 App 的路线，原移动技术栈继续有效。
