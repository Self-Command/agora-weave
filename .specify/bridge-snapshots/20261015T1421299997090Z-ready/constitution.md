# 项目宪法

本宪法规定跨功能适用的工程原则、长期技术约束与治理规则，作为规格、设计、实现和交付的合规基线。

## 核心原则

### 一、代码质量与可维护性

代码必须职责清晰、模块边界明确，并通过可测试的契约协作。优先使用框架和现有依赖的成熟能力，
避免重复实现；新增抽象、依赖或复杂度必须有明确需求与维护成本依据，不引入无必要抽象或过度设计。

### 二、架构与扩展安全

核心身份、权限、安全、配置和审计能力必须保持独立有效，不因业务模块停用或卸载失效。
扩展必须通过明确契约接入，并隔离权限、数据与环境。版本、依赖、兼容条件、迁移和恢复限制
必须可识别、可检查；变更不得破坏核心边界，不得承诺未经验证的无损恢复。

### 三、安全、隐私与 AI 边界

系统必须遵循最小权限与最小必要数据原则，由服务端检查当前身份、资源及操作授权。
密钥和高权限凭据不得暴露给客户端或公开产物。产品内 AI 助手及其 MCP 能力必须保持只读，仅处理获准数据；
开发 AI 必须遵守第九条规定的授权范围。工具、缓存、历史授权或高权限凭据不得绕过当前访问限制；
撤权后，系统可控的后续新访问必须立即按当前资格拒绝。

### 四、测试与真实验证

验证必须覆盖适用的功能、接口、权限与安全、集成、回归及端到端行为，并取得真实运行证据。
静态检查、编译成功或 mock 演示不能单独证明产品行为正确。结果及必要证据必须关联实际提交、
产物与执行环境；必需验证失败、跳过、取消、超时、环境不可用或缺失结果，均不得表述为通过。
修复后必须重新验证受影响行为并完成必要回归。

开发验证与正式验收必须分层。每个新增行为或缺陷先在健康云端通道取得目标语义断言的真实 Red，
读取失败因果后才实现；Green 使用相同 oracle 与夹具，执行受影响套件及必要回归。
开发中不要求每次提交无条件重跑完整平台矩阵；验证范围必须依据实际变更、依赖及风险确定，
未知影响采用完整适用集合，不得以快速反馈、缓存或缩减清单冒充 Green 或验收。

云端构建、非空测试执行与所需隔离服务健康等基础通道经真实核验后，可准入依赖它们的业务开发；
不影响该行为验证的 CI 证据、采集或审查完备性问题可并行修复，并如实保留未完成状态。
基础通道故障、目标 Red／Green 不可认证或安全边界未知时，暂停依赖工作。
开发就绪不能代替正式 CI 就绪、任务验收或交付通过。

合并、阶段验收交付或发行前，必须在同一最终提交及匹配产物上完成全部适用验证，
包括最低与当前受支持系统、权限与安全、真实交互，以及当前代码和实际图像审查；
具体范围由已批准规格及验收契约确定。缺失、失败、跳过、取消或无法判断的必需结果仍阻止通过。
尚待正式验收的工程移交或 Draft PR 必须明确其范围、已有证据和未决项，不得表述为已验收、可合并或已发行。

### 五、云端交付约束

全部编译、构建、测试、回归、实际运行及视觉和交互验收，必须通过 GitHub Actions 在云端执行并记录。
本地电脑不得运行项目、测试或验收，也不得作为替代 runner；本地文件编辑、代码阅读和 Git 操作可以进行。
生产常驻服务必须独立部署；开发、测试与生产的数据、凭据和副作用必须相互隔离。

### 六、用户体验与原生可用性

各端及扩展必须保持一致的组件语义和状态表达，并适配平台交互、字体缩放、可读对比度、触控区域、
读屏、焦点与安全区。错误、加载、不可用及权限变化必须提供真实、可理解的反馈，不显示假成功。
原生可用性与视觉、交互结论必须来自对应客户端的实际运行，不能由静态稿或其他端的演示替代。

### 七、性能与资源纪律

性能判断必须来自可复现的实际测量，并记录环境、数据规模、负载与测量口径。
资源使用、依赖引入及额外基础设施必须有明确必要性与成本依据，不作无依据的性能承诺。
具体指标与资源配置由对应规格和技术计划确定并验证，不以预估或过度设计代替测量。

### 八、生产代码与界面内容

生产代码、注释、界面文案、无障碍文本、资源及运行时输出，必须只保留服务真实产品功能、运行、
安全与维护的必要内容。不得残留 AI 自评、任务进度、开发对话、测试过程叙述及其他与生产用途无关的内容。

内容必须依据实际用途区分，不得因清理误删必要注释、测试标识、真实产品功能、测试报告或验证证据。
工程过程资料必须独立维护，不混入生产代码或产品界面；清理不得削弱已确认功能或降低验证要求，
相关结论必须有对应最终版本的有效云端证据支持。具体例外判定与检查规则由相应工程规范或验收资料承载。

### 九、用户决策与开发协作

AI 必须在用户已经批准的目标、方案和约束内工作，不得擅自改变已确认要求、替换技术或服务、
删减功能、降低验收标准、绕过限制或采用未经授权的替代方案。无法在既定条件下解决的阻塞，
必须如实报告并请求用户决策。

- 实质性冲突涉及已确认需求、产品范围、技术栈、权限、安全、隐私、数据处理、验收标准或实际行为。
  无论冲突来自新提示词、开发资料、技能规则或实现，必须说明冲突内容、影响范围与可选方案，
  等待用户明确决定后，才能执行受影响的工作。
- 非实质性问题仅限不改变已确认需求、系统行为、安全边界或验收结果的文字歧义、排版问题与文档格式差异。
  可以依据已有明确规则整理和纠正，并记录必要变更，无需逐次请求用户确认。

等待决定时，只暂停依赖该决定的修改与操作；其他不受影响且已经授权的工作和只读调查可以继续。
用户已明确决定或已按授权规则解决的事项不得反复询问；出现新的实质性冲突时，仍必须重新确认。
用户沉默、超时、预选选项或其他 AI 的自行判断，均不能替代用户对实质性决策的明确批准。

本项目的实质性决策规则优先于 SP、SK 等技能允许的自行裁决、合理猜测或默认继续策略；
记录裁决不能代替取得用户确认。相关开发资料必须反映已确认决定；决策与必要变更记录由独立工程资料承载，
不进入生产代码或产品界面。

## 长期技术约束

- 移动端使用 Expo、React Native 和 Expo UI，覆盖 iOS 与 Android。
- 后端使用 Supabase 官方 Docker Compose 自托管。
- 管理后台基于 Kiranism 的 Next.js、shadcn/ui 模板，适配真实身份、权限和业务。
- 具体版本、部署参数和工具组合由技术规划核验并记录，不在宪法中预先指定。

## 文档职责

产品需求与业务规则由 PRD 和功能规格承载；技术实现方案由技术计划承载；页面、视觉风格与具体交互
由设计规格承载；实施步骤由任务清单承载。宪法仅规定跨功能工程原则、不可突破的技术约束与治理规则，
不重复各类文档的细节。从宪法移除产品内容或引用不撤销原有要求，相关资料继续承担其职责。

## 治理

- 实质原则或技术约束变更必须说明原因、影响、需同步的资料及必要迁移安排，并取得用户确认后生效。
  文案澄清不得隐含行为变化，工程方案或模板惯例不得自行豁免原则。
- 使用语义化版本：不兼容的原则删除或重定义升主版本；新增原则或实质扩充升次版本；
  不改变语义的澄清与纠错升修订版本。
- 规格与技术计划审查、代码变更审查及交付审查必须核对适用原则和实际证据。
  发现违规须记录影响并修正；未解决的违规不得将相关变更或交付标记为合规、通过。
  确需改变原则时，必须走修订程序，不能只凭理由说明绕过约束。
- 每次修订必须维护版本、批准依据和最后修订日期；首次批准日期保留历史事实，未知时如实标记。
